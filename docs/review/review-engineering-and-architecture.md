# Independent Review: Engineering and Architecture

*Review date: 2026-10-23. Scope: the full source tree of `tallyard-app` (all modules under
`io.tallyard.*`, `V1__core_schema.sql`, `application.yml`, every test under `src/test/java`), the
README, `docs/architecture/architecture.md`, `docs/architecture/failure-model.md`, ADR-001 to ADR-007,
and the acceptance-criteria and testing-strategy documents. No file in this repository was modified
other than this report.*

*Two findings were verified empirically rather than by reading alone. A throw-away copy of the
repository was made under `/tmp`, one probe integration test was added **to the copy only**, and the
probe was run with Testcontainers (PostgreSQL 17, Kafka 4.1) through the project's own Failsafe
configuration. The copy was deleted afterwards. The probe output is quoted verbatim in TY-01 and
TY-08.*

Two reviewers, two lenses:

- **Reviewer A — Senior Java Engineer.** Java and Spring quality, structure, domain modelling,
  exception handling, transaction boundaries, tests, maintainability.
- **Reviewer B — Staff Software Architect.** Boundaries, distributed consistency, messaging
  semantics, failure behaviour, scalability ceilings, data ownership, and whether the documentation
  describes the code that exists.

---

## 1. Scores

| Reviewer | Score | Justification |
|---|---|---|
| **A — Senior Java Engineer** | **6.5 / 10** | The codebase reads as the work of someone who knows modern Java and Spring well: records and immutable views across module boundaries, package-private internals verified by Spring Modulith and ArchUnit, a genuinely pure `RatingEngine` with example and property tests, JDBC where it matters and JPA where invariants matter, a single injectable `Clock`, RFC 9457 errors with stable codes, Spotless and JaCoCo wired in. Transaction propagation is mostly deliberate (`MANDATORY` on the outbox and period locks, explicit `flush()` where Hibernate ordering bites). What keeps the score out of the 8s: a **Critical, reproducible bug in a headline feature** (rating any customer who holds prepaid credit fails with an FK violation, TY-01) that the 77-test suite never exercises; a verified pricing bug for non-additive aggregations (TY-08); catching a constraint violation inside a JPA transaction and continuing (TY-09); a scheduler that does 25 ratings in one transaction with no per-item isolation (TY-02); and an acceptance-criteria document whose test names do not match the suite (TY-16). These are the kinds of defects a second reviewer on a real team would have caught, and they sit in exactly the paths the README advertises. |
| **B — Staff Software Architect** | **6.0 / 10** | The decomposition is sound and the guarantees are stated with unusual honesty ("effectively-once", bounded staleness, explicit non-guarantees). The lock protocol between metering (`FOR SHARE`) and rating (`FOR UPDATE`) is real and lives inside the right transactions; the outbox is correctly `MANDATORY`; ack-after-commit is real; the dependency inversion through `UsageSource` is the right way to break the metering/billing cycle. However, the two flagship claims hold only when the consumer is caught up: "replay as of `rated_at`" is implemented with a **producer-side** timestamp (TY-03), so the very failure drill the README showcases (kill the worker, let lag build) produces invoices whose replay cannot match; rating is driven by wall-clock `grace_until` and ignores consumer lag (TY-04), so after an outage usage silently becomes next-period adjustments. The webhook consumer swallows infrastructure failures and acks (TY-05), contradicting the failure model. The outbox's "ordered per aggregate" guarantee is not met with two publishers or after a failed batch (TY-07). Negative catalog caching turns the most common onboarding sequence into permanently uncounted usage (TY-06). None of these are exotic; they are the ordinary distributed-systems edges the documentation claims to have handled. |

## 2. What is genuinely good (so the findings are read in proportion)

- Module boundaries are compile-time facts, not intentions (`ModularityTest`, `ArchitectureTest`), and
  the only cycle-breaking inversion (`billing.UsageSource` implemented by metering) is documented and
  correct.
- The hot path is set-oriented and idempotent: multi-row `INSERT … ON CONFLICT DO NOTHING RETURNING`
  (`UsageEventStore.insertNew`), batched bucket upserts with `LEAST/GREATEST/CASE`, deterministic
  bucket ordering to avoid upsert deadlocks, in-batch deduplication before the insert.
- The period lock protocol is implemented exactly as ADR-003 describes: `lockPeriodCovering` and
  `lockOpenPeriod` are `Propagation.MANDATORY` and are called from inside `MeteringService.process`
  (`@Transactional`), so the shared lock is held for the whole batch transaction; `rateLocked` takes
  `FOR UPDATE`; the scheduler claims with `SKIP LOCKED`; `@Version` is a second line of defence.
- `RatingEngine` is pure, exact to six decimals, rounds HALF_EVEN per line, and the property tests are
  the right properties (monotonicity, band decomposition, volume ≤ graduated).
- Credit consumption locks grants in a deterministic order and the schema carries the invariant
  (`CHECK (amount_consumed <= amount_granted)`), proven by a 16-thread test.
- Security basics are right: hashed keys, tenant id only from the key, scopes via `@PreAuthorize`,
  constant-time comparisons, AES-GCM for webhook secrets, Stripe-style signed webhooks.

## 3. Findings

Severity: **Critical** = wrong money or a core feature unusable; **High** = a stated guarantee is
false or data is silently lost; **Medium** = correctness or scalability defect with a bounded blast
radius; **Low** = quality, hygiene, or documentation drift.

Type: **Objective defect** = demonstrable from the code or by execution; **Subjective opinion** =
design judgement on which reasonable engineers may differ.

| TY-02 | **Critical** | Objective defect | `billing/internal/BillingService.java:289-312`; `billing/internal/BillingScheduler.java:28-46` | `closeDue`, `rateDue` and `finalizeDue` each process up to 25 periods in **one** transaction. | TY-03 | **High** | Objective defect | `metering/internal/UsageEventStore.java:235-241` (`ingested_at < ?`); `ingestion/internal/IngestService.java:94` (`ingestedAt = clock.instant()` on the API node); `billing/internal/BillingService.java:250-252`; `billing/UsageSource.java:13-16` | "Replay as of `rated_at`" filters the log on `ingested_at`, which is the **API-side receive time**, not the time the row became visible in PostgreSQL. Replay then reports `matches=false` on a correct invoice, and the "proof" is meaningless whenever lag exceeds zero. The same mechanism makes replay disagree with buckets whenever an event was rejected (`NO_MATCHING_METER`, `NO_ACTIVE_SUBSCRIPTION`) and the catalog was later fixed: replay recomputes with *today's* catalog, not with what was counted. Clock skew between API nodes adds to this. `BillingLifecycleIT.lateEvent…` passes only because the late event is ingested after rating. | Make replay membership-based rather than time-based: record which period each event was attributed to in the batch transaction (e.g. `usage_event.counted_period_id uuid` set by `MeteringService`, or a `usage_event_attribution(usage_event_id, meter_id, period_id, kind)` table), and replay = "events attributed to this period for this meter". | TY-04 | **High** | Objective defect | `billing/internal/BillingRepositories.java:47-51`; `billing/internal/BillingService.java:296-304`; ADR-003 "Locking protocol" | Rating is triggered by wall clock (`grace_until <= now`) and is blind to consumer lag. After a worker outage (or simply a long Kafka backlog) the restarted worker's scheduler closes and rates periods while its own consumer is still draining events that belong to those periods. Those events become adjustments on the *next* invoice — financially carried forward, but the invoice for the period is materially wrong, the customer sees a confusing adjustment line a month later, and TY-03 makes the replay fail. ADR-003's grace window ("stragglers still land in the period") is defeated by the one failure mode it is meant to cover. | Gate `rateDue` on a metering watermark: per partition, the max `ingested_at` committed by the consumer (persist it in the batch transaction), and only rate a period when `min(watermark) >= grace_until` (or lag == 0 from `KafkaAdmin`). Expose the watermark as a gauge and in the runbook. |
| TY-05 | **High** | Objective defect | `webhooks/internal/BillingEventsConsumer.java:35-48`; contradicts `docs/architecture/failure-model.md:38` and `architecture.md:338` | The `billing.events.v1` consumer catches **every** `RuntimeException` from `webhooks.enqueue(...)` — including `CannotCreateTransactionException`, `DataAccessResourceFailureException`, lock timeouts — logs "Skipping unreadable billing event", and acknowledges the offset. | TY-06 | **High** | Objective defect | `catalog/internal/CatalogService.java:41-54, 258-265, 288-293`; `metering/internal/MeteringService.java:116-126`; `failure-model.md` row "Unknown subject / meter" | The worker caches **negative** lookups: `customersByExternalId` stores `Optional.empty()` and `metersByType` stores an empty list for 15 s; write-side invalidation is node-local (the API node). | TY-07 | Medium | Objective defect | `outbox/internal/OutboxPublisher.java:100-108, 150-158`; claims in ADR-006, README:124, `failure-model.md:16`, `architecture.md:151` | "Published … in order per aggregate" is not guaranteed. (b) On any send failure the *whole* batch gets `next_attempt_at` pushed back; rows created later for the same aggregate become eligible first and are published before the older ones. ## 5. Top 5 fixes to make before publishing

1. **Fix credit application ordering and cover it with a test (TY-01).** Persist the invoice before
   `credits.apply`, remove the premature `flush()`, add an integration test that rates a customer
   holding a grant and asserts `creditsApplied`, the ledger row and `credit.depleted`. Until this is
   fixed, the "prepaid" plan in the demo and every prepaid customer in production cannot be invoiced.
2. **One period per rating transaction, with a failure record (TY-02).** Claim with `SKIP LOCKED`,
   rate in `REQUIRES_NEW`, store attempts and last error on the period, emit a metric. One bad period
   must never stop rating for everyone.
3. **Make replay membership-based and rating lag-aware (TY-03, TY-04, TY-18).** Record the period each
   event was attributed to inside the batch transaction and replay from that attribution; gate
   `rateDue` on a metering watermark. This is what turns "replay-provable" from a slogan into a
   property that survives the README's own chaos drill.
4. **Stop losing billing events on transient failures (TY-05, TY-09).** Catch only parse errors in
   `BillingEventsConsumer`; replace the catch-DIVE idempotency in `WebhookService.enqueue` with
   `ON CONFLICT DO NOTHING`.
5. **Remove negative catalog caching from the metering path and add a re-count command (TY-06, TY-08).**
   Do not cache `Optional.empty()`/empty meter lists for 15 s on the worker; restrict late-event
   adjustments to additive aggregations; provide an operator command to re-count stored events for a
   subject after a catalog fix.

After these, align `acceptance-criteria.md` with the real test names and add the four missing
integration tests named in TY-16; the documentation is otherwise unusually good and deserves code that
matches it.
